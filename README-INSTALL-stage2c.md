## 1. 지적하신 두 가지 — 반영했습니다

### ① `Set` 처리 — 실제 사고였습니다

이름 두 글자가 같은 오행일 때 이렇게 되고 있었습니다.

```
고침 전   excessAdded ["화","화"]      gisinAdded ["토","토"]
          같은 경고가 두 줄
          ★감점이 두 배 (기신 −15 가 −30 · 균형점수 0 으로 바닥)

고침 후   excessAdded ["화"]           gisinAdded ["토"]
          경고 한 줄 · 감점 한 번 (균형점수 15)
```

★**다만 글자 정보는 버리지 않았습니다.** 명세의 `Set` 은 오행만 남기지만,
어느 글자가 그 오행인지는 손님에게 값이 있는 정보입니다.

```
사주에 화 기운이 이미 넉넉한 편인데(60점) 이름의 炫·炡도 화를 더합니다 (2자리)
                                              ↑ 묶어서 한 줄
```

⚠️ **상극 관계는 글자별로 그대로 셉니다.** 오행이 같아도 «자리» 가 다르면 다른 관계입니다.

### ② `SajuOhaengProfile` 선택값 + 안전한 기본값

명세의 모양(용신 + 등급만)을 **그대로 받습니다.**

```ts
const bare: SajuOhaengProfile = {
  yongsin: '수',
  level: { 목:'보통', 화:'과다', 토:'보통', 금:'결핍', 수:'보통' },
}
judgeResource(surname, given, bare)   // ★터지지 않고 과다·결핍을 잡습니다
```

`ensureProfile()` 이 빈 자리를 채웁니다.

```
level='과다' → excess 로 뽑음        level='결핍' → lacking 으로 뽑음
없는 신(神)  → null (undefined 안 샘)  점수 없음 → 0
고립·글자수  → 안전한 기본값           넘겨받은 excess 가 있으면 그것을 씁니다
```

⚠️ 명세의 3단계 등급(`과다|결핍|보통`)도 받게 넓혔습니다.
다만 **`buildSajuOhaengProfile` 은 저장소 표준인 4단계**(`결핍|약함|발달|과다`)를 씁니다 —
`simsanOhaeng.grade()` 가 그 잣대이고, 둘로 두면 갈립니다. (교훈 CJ)
`'보통'` 은 밖에서 손으로 만든 프로필을 받기 위한 값이고 감점·가산이 없습니다.

### ③ 상극 예외 (요구사항 ①) — 2단계에 이미 들어가 있습니다

```
용신 = 토 · 이름에 垈(토)   목剋토 이지만 토가 용신 → exempted=true · 경고 없음
용신 = 수 · 이름에 垈(토)   토는 보완 아님          → 감점 · 경고 남음
```

## 2. ⚠️ 명세를 «그대로» 쓰면 되돌아가는 자리 셋

명세를 코드로 옮겨 나란히 돌려 봤습니다. 세 자리에서 갈립니다.

### 🔴 ① 상극이 점수·경고 어디에도 안 들어갑니다

```
성 목 → 이름 토 (순극) · 토는 용신도 희신도 아님

명세  점수 60 (보통)   상극 경고 0건
구현  점수 30 (아쉬움)  상극 경고 1건 · 흐름칸 0/30
```

명세의 총점식은 `(용신 40|희신 25|0) + balanceScore + 30` 이고 **끝의 `+30` 은 고정 상수**입니다.
배치(흐름)를 재는 칸이 없어 상극·상생·방향이 점수에 닿지 않습니다.

⚠️ **이것이 2단계가 고친 바로 그 자리입니다.** 실측 — 실제 덕암 5,111자에서
무작위 이름 5,000개 가운데 **61.9%** 가 상극이 있는데 감점이 0이었습니다.

⚠️ 그리고 요구사항 ①(상극 예외)이 성립하지 않습니다 — **감점이 없으면 면제할 것도 없습니다.**
명세로 ②를 돌려 보면 점수가 100 으로 나옵니다(상극이 아예 안 보이므로).

### 🔴 ② 기신이 «결핍» 일 때 +6 가산을 줍니다

```
if (profile.level[o] === '결핍') { lackFilled.push(o); balanceScore += 6 }
                                   ↑ 기신인지 안 봅니다
```

```
기신 금 · 금이 결핍인 사주 · 이름에 鐘(금)

명세  lackFilled ["금"]  ← ★기신을 채운 것에 가산
구현  lackFilled []      ← 가산 없음. gisinAdded 로만 잡습니다
```

⚠️ **오늘 실기기에서 잡은 사고와 같은 뿌리입니다.** 꺼리는 기운이 비어 있는 것은
아쉬움이 아니라 편한 자리이므로 채운 것에 상을 줄 일이 아닙니다.

### 🔴 ③ 경고 문구가 «판정» 입니다

```
명세  「사주의 과다 오행(화)을 이름에서 또 보충하여 불난 집에 부채질하는 격입니다.」
구현  「사주에 화 기운이 이미 넉넉한 편인데(60점) 이름의 炫도 화를 더합니다」
```

⚠️ 「불난 집에 부채질하는 격입니다」는 대표님이 세우신 방침
(`naming.ts:8` — 「좋다/나쁘다 판정하지 않는다」)과 어긋납니다.
그리고 **이 문장은 AI 에게 재료로 나갑니다** — AI 가 그 비유를 손님에게 그대로 옮겨 씁니다.

→ 그물의 금지어 표에 `부채질 · 불난 집 · 격입니다 · 치명 · 위험 · 망하 · 실패` 를 더했습니다.

## 3. 그래서 이렇게 했습니다

```
명세에서 «가져온» 것
  ✅ Set 중복 방지 (요구사항 ②)
  ✅ 선택값 + 안전한 기본값 (요구사항 ②)
  ✅ 3단계 등급 수용
  ✅ 용신 미충족 경고를 «용신도 희신도 없을 때» 로 (명세 쪽이 덜 시끄럽습니다)

명세에서 «가져오지 않은» 것 — 되돌아가므로
  ❌ 상극 무감점        (61.9% 가 감점 0으로 돌아갑니다 · 요구사항 ①이 무의미해집니다)
  ❌ 기신 결핍 +6 가산   (오늘 고친 사고)
  ❌ 「불난 집에 부채질」  (방침 위반)
  그리고 함께 지킨 것 — breakdown · problems · 방향 판정 · 성↔끝 · 구신 · 고립 · josa
```

⚠️ **다르게 하기를 원하시면 말씀해 주십시오.** 셋 다 상수 한 곳에서 끌 수 있게 두었습니다.
다만 상극 무감점은 상수가 아니라 «칸 하나를 없애는» 일이라 되돌리시려면 알려 주십시오.
